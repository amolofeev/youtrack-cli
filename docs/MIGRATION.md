# План миграции yt в независимый git-репозиторий

Версия: **0.1** · Статус: **черновик (на согласование)** · Дата: 2026-08-02
Задача: [#53](https://github.com/amolofeev/prompt-and-pray/issues/53) · Родитель: #5

Документ описывает перевод подпроекта `yt` из поддиректории монорепозитория
`prompt-and-pray` в отдельный git-репозиторий. **Это план, а не исполнение**:
миграция выполняется отдельными задачами, которые создаются ПОСЛЕ согласования
этого документа (см. §7 «Этапы исполнения»).

Источники фактов: корневой `AGENTS.md`, `yt/AGENTS.md`, `yt/docs/structure.md`,
`docs/SPEC.md` (rev 1.1.1), `docs/PLAN.md`, `docs/PROGRESS.md`, `opencode.jsonc`,
`.github/workflows/ci.yml`, `VERSION`, `git log` (95 коммитов, 55 из них затрагивают `yt/`).

## 2. История и перенос git

### 2.1 Варианты

| Вариант | Инструмент | Плюсы | Минусы |
|---|---|---|---|
| **A. subtree split** | встроен в git: `git subtree split --prefix yt -b yt-history` | нет установки ПО; история yt-коммитов (55 шт.) переносится, `[AI] #N`-сообщения сохраняются; первый коммит — bootstrap `a6c157d` | не захватывает историю root-артефактов (VERSION, ci.yml — по 1 коммиту, теряются как отдельные коммиты, контент заносится «импорт-коммитом»); требуется локальный репо в состоянии без незакоммиченного мусора |
| **B. git filter-repo** | `git filter-repo --path yt/ --path VERSION --path .github/workflows/ci.yml --path-rename yt/:` | полный контроль: захватывает и yt/, и root-артефакты, умеет чистить секреты (`--strip-blobs-with-ids`, анализ) | требует установки `git-filter-repo` (Python/pip — по правилам спросить человека); сложнее в обвязке (свежий клон, `--force`) |
| **C. свежий репозиторий** | `git init` + импорт-коммит | максимально чисто; нулевая работа с историей | вся история теряется: обоснования решений (`[AI] #N`), ссылки на атомы; для маленького проекта допустимо |

### 2.2 Что попадает в историю (вариант A)

- Коммиты, меняющие только `yt/`: переносятся целиком (пути `yt/foo` → `foo`).
- Коммиты, меняющие и `yt/`, и корневые файлы: остаются, но содержат только diff по `yt/`
  (root-изменения отбрасываются — они не пушились как «пустые»).
- Коммиты, не затрагивающие `yt/` (VERSION `79a92c0`, CI `2b81160`, meta-коммиты
  про `.opencode/`): отбрасываются. Их контент вносится **импорт-коммитом** в целевом
  репо (VERSION, ci.yml, SPEC/PLAN — текущее состояние, история по 1 коммиту не ценна).
- `git subtree split` не трогает контент файлов, только дерево (переименование путей),
  поэтому коммиты остаются пушей-безопасными и не требуют force-push после вставки
  в новый репо.

### 2.3 Влияние переписывания путей на бинарную часть

**Не имеет.** Go-импорты внутри исходников ссылаются на путь модуля
(`github.com/amolofeev/prompt-and-pray/internal/...`), а не на раскладку каталогов репо.
Перенос `yt/` → корень меняет только дерево коммитов; при одинаковом коде и одинаковых
`-ldflags` `go build` даёт байт-в-байт тот же бинарь.

Бинарь меняется только при **переименовании модуля** (R2): меняются символьные ключи
`-X github.com/amolofeev/yt/internal/version.Version=...` и строка `main`-импорта
(`yt/bin/yt` gitignored, на репозиторий не влияет). Поведение утилиты не меняется.
Golden-тесты версии задают значения через `setVersionForTest` и от модуля не зависят.

### 2.4 Рекомендация

**Вариант A (`git subtree split`)** как рабочий: история нужна (55 коммитов с
обоснованиями и ссылками на атомы #16–#52), инструмент встроен, root-артефакты имеют
по одному коммиту и не стоят установки filter-repo. Вариант B — если владелец захочет
полную историю и/или гарантированную чистку секретов в один проход. Вариант C — только
если история сознательно не нужна.

### 2.5 Аудит секретов

Перед публикацией нового репо проверить историю и дерево:
- `git log --all -p | grep -Ei 'perm:|token|Bearer|api[_-]?key|password'` — ожидаем пусто
  (конфиг с токеном никогда не коммитился; `.opencode/openapi.json` gitignored).
- `git ls-files | grep -iE 'config|\.env'` — в дереве не должно быть конфигов с токеном.
- При варианте B дополнительно: `git filter-repo --analyze` до публикации.
- Памятка для целевого репо: `.gitignore` обязан включать `.opencode/*_memory.md`,
  `.opencode/openapi.json`, `bin/`, `vendor/` (см. §3.5).

## 5. Версионирование и релизы

### 5.1 Источник версии

- `VERSION` (сейчас `0.0.1-pre-alpha`) переезжает в корень целевого репо и остаётся
  единственным источником версии (`yt version` и `--version`, SPEC §1.4, #21).
- Релизный тег создаётся из него: `git tag "v$(cat VERSION)"`.
- Альтернатива на будущее (отдельная задача): выводить версию из `git describe --tags`
  и убрать файл VERSION. Пока не требуется.

### 5.2 Релизный процесс (R4)

- Рекомендация: GitHub Actions `release.yml` — триггер push тега `v*`:
  1. `actions/setup-go@v5` (1.24.0);
  2. матрица `os: [ubuntu-latest, macos-latest]`, `GOARCH: [amd64, arm64]`;
  3. `make build` с `GOOS`/`GOARCH`, артефакт `bin/yt` → `bin/yt-<os>-<arch>`;
  4. `sha256sum` → `checksums.txt`;
  5. `softprops/action-gh-release` (или `gh release create`) — ассеты + чексуммы.
- Альтернатива: **goreleaser** (`goreleaser.yml`) — удобнее (homebrew/нативные пакеты),
  но добавляет зависимость и конфиг; отложить до появления спроса на дистрибуцию.
- `bin/yt` в репо не хранится (gitignored) — артефакт только в релизе.
- Проверка: из скачанного `bin/yt` выполнить `yt version` (должна быть версия из тега,
  commit — short hash) и `yt --version`.

## 7. Этапы исполнения (после согласования)

Каждый этап — отдельная задача со своим DoD; каждый шаг проверяем.

### Этап M1 — Подготовка и перенос истории
- [ ] Локальный репо без незакоммиченного мусора; создать целевой пустой репо на GitHub
  (имя — решение владельца) и пустой клон.
- [ ] `git subtree split --prefix yt -b yt-history` в монорепо.
- [ ] В целевом репо: `git fetch <monorepo> yt-history` → `git checkout -b main FETCH_HEAD`.
- [ ] Импорт-коммит: `VERSION`, `.github/workflows/ci.yml`, копии `docs/SPEC.md`/`docs/PLAN.md`,
  объединённый `.gitignore`, `LICENSE`, `AGENTS.md`, `docs/MIGRATION.md`, `.opencode/yt_memory.md`
  (локально, gitignored).
- **Проверка:** `git log --oneline` содержит bootstrap `a6c157d` первым и все yt-атомы;
  `git ls-files` = ожидаемый набор §3.1; аудит секретов §2.5 — чисто.

### Этап M2 — Модуль и сборка в целевом репо
- [ ] Решение R2; при переименовании: `go mod edit -module ...` + массовая замена импортов
  (30 файлов) + ldflags в Makefile.
- [ ] Makefile: `VERSION := $(shell cat VERSION)`.
- [ ] CI: `.github/workflows/ci.yml` портирован без `working-directory: yt`, `cache-dependency-path: go.sum`.
- **Проверка:** `gofmt -l .` пусто; `make vet`, `make lint`, `make build` зелёные;
  `go mod tidy` без diff; `make test` — покрытие api/config/output ≥70%;
  `yt version` показывает версию из VERSION; `--json` валиден (`jq`).

### Этап M3 — Версионирование и релиз

- **Проверка:** скачанный `bin/yt-<os>-<arch>` — `yt version`/`yt --version` корректны;
  чексуммы совпадают (`sha256sum -c checksums.txt`).
